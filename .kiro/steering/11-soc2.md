# SOC 2 Impact Rule (Part 23.1)
Every design.md MUST fill a "SOC 2 impact" section. No exceptions.

## Criteria in scope
Security (mandatory) + Availability + Confidentiality.
Processing Integrity added at Type II (immutability story).

## What the section must state
1. Which Trust Services Criteria the feature touches (CC1–CC9, A1, C1, PI).
2. Which controls are exercised (from the Part 23.1 control map).
3. What evidence is emitted automatically (audit events, Config rules, etc.).

## Key controls already architected (cite, don't rebuild)
- CC1/CC2: Policies authored & version-controlled in Cumplify's own tenant;
  role definitions (Part 13). Evidence: M1 controlled docs + acknowledgments.
- CC3/CC4: Cumplify's own M5 risk register; Security Hub findings triaged as
  NCs into M2. Evidence: Security Hub → EventBridge → NC records.
- CC5: SoD engine + HITL gates + permission sets → AUDITLOG events.
- CC6: Cognito MFA + ABAC + quarterly access-review job.
- CC6.6/6.7: 10 CMKs, TLS everywhere, VPC endpoints, WAF. Evidence: Config rules.
- CC7: GuardDuty + Security Hub → incident records in M2 (10.2).
- CC8: CDK Pipelines only path to prod; CDK Nag = fail; PR required.
- CC9: Subprocessor register in Cumplify's own M8.
- A1: SLOs + DR runbooks + AWS Backup vault-lock.
- C1: Tenant isolation battery (01-tenancy-rules.md) + retention engine.
- PI: Hash-chained trail + WORM + daily chain-verification job.

## Cumplify's own posture (Part 18.4)
Runs its own QMS/ISMS in-tenant. SOC 2 Type I at GA, Type II GA+9mo, 27001 year 2.

## Evidence fabric (Appendix D)
Org CloudTrail, Config SOC 2 conformance pack, Security Hub, GuardDuty,
Inspector, IAM Access Analyzer, Audit Manager, AWS Backup vault-lock.

## Why this rule
SOC 2 Type I at GA. If a feature cannot state its SOC 2 impact, it either has
none (unlikely for anything touching data) or the designer hasn't thought about it.
